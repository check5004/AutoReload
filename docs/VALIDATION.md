# 検証記録

2026-09-14 / リリース 0.2.0

## ローカルで実施

- JavaScript構文、Manifest V3、アイコン、バージョン整合性、HTMLからのローカル参照：合格。
- Node.jsテスト24件：合格。日付・閏年、混雑／待機列判定、間隔と上限、設定入力、更新比較、権限、ドメイン分離、同時開始、古い実行IDの拒否、更新通知、ZIPの構造に加え、練習ページの独立した保存先とメッセージ制限を検証。
- 分離したChromium 151のプロファイルへ拡張機能を読み込んだ17シナリオ：合格（テストランナーでは親テスト込み19件）。
- 内蔵ページのテストは配布用Manifestをそのまま使用し、オフライン・追加のホスト権限なしで実施。
- 通常のHTTPページへの挿入も、一時的なlocalhostのテスト用サイトで従来の11シナリオを検証。

## 内蔵の練習ページで確認したシナリオ

1. 設定画面・ポップアップから内蔵HTMLを開き、既存の練習タブを再利用する。練習用の設定画面も正しい保存先で開く。
2. 復旧の目印、受付前ボタン、入力欄をクリックで記録し、実行しない対象プレビューが動作する。
3. 記録後に日付だけを変え、発売後に現れる目的の公演を選択。ID・並び順が変わったフォームを入力し、最終確認で止まる。
4. 混雑画面から内蔵HTMLを実際に再読み込みし、進捗を維持して復旧を検知する。
5. 複数の練習タブを開いていても、指定したタブだけで記録を開始する。
6. 購入サイトの設定を保持したまま練習をON/OFFでき、再読み込みでも記録した操作を保持する。ガイドへ移動すると実行を停止する。

## 通常のHTTPページで確認したシナリオ

1. 無効な発売前ボタンと入力欄をクリックで記録し、記録中には遷移・送信しない。
2. 発売開始までは存在しない対象を待ち、日付・席種で選択する。翌日にIDと並び順が変わった入力欄も埋め、最終確認で止まる。
3. 混雑ページを再読み込みして復旧し、その後は再読み込みしない。
4. 同じ条件の候補が複数ある場合に停止する。
5. 認証・順番待ちの文言がある場合に停止し、再読み込みしない。
6. 同一ドメインの実際のページ遷移をまたいで進捗を保持し、購入確定を拒否する。
7. 利用者の手動入力で監視を停止する。
8. CSSで隠された混雑・認証文言では誤検出しない。
9. 予約時刻まで待ち、一度の開始リロード後に入力する。
10. 設定画面の保存と、ドメインOFFによる停止・設定保持。
11. 最後の許可されたリロードで復旧を検知し、未設定の入力変数があっても復旧監視を継続する。

## CI

`Validate` は Windows / Ubuntu のロジック・配布テストと、Ubuntuの実ブラウザーテストを実行します。`Release` は同じ検証を配布の前提にします。最新の結果は [Actions](https://github.com/check5004/AutoReload/actions) を参照してください。

## 未検証・制限

実在の販売サイト、実際の在庫競争・決済、Chromeのネイティブ権限確認画面、OSスリープからの厳密な時刻復帰は検証対象外です。サイト固有の項目認識は、対象を記録しプレビューで確認してください。機能範囲は README の「対応範囲」を参照してください。
